# 案例故事系统

## 案例功能

一个案例至少承担一种功能：

- **提供证据**：证明主张不是空话。
- **解释机制**：让抽象逻辑变具体。
- **增加趣味**：打破干燥论述。
- **制造情绪**：让读者感到惊讶、共鸣、愤怒、安心或好奇。
- **降低理解成本**：用熟悉场景解释复杂概念。
- **处理异议**：回答读者心里的“不一定吧”。
- **增强转化**：让 offer、CTA 或行动更可信。
- **制造记忆点**：让内容有可复述的场景。

没有功能的故事应删除。

## 案例类型

### 真实历史事件

适合支撑规律、机制、反常识观点。

要求：

- 标注“需要核验”
- 需要具体使用时由 `$cflow-research` 核查来源、时间、人物、因果和关键细节
- 不凭记忆补细节
- 不把复杂历史简化成单因果
- 适合后续补来源

### 个人经历

适合建立作者可信度和人味。

要求：

- 保留具体场景
- 不擅自美化结果
- 允许有不完整和毛边

### 用户/客户案例

适合营销、服务、产品、社群、课程内容。

要求：

- 区分匿名、脱敏、公开案例
- 标注结果是否有数据支撑
- 明确前后变化和关键动作

### 行业案例

适合解释趋势、商业机制、平台变化。

要求：

- 说明行业背景
- 涉及当前行业、公司、产品、价格、政策或平台变化时，正式研究交给 `$cflow-research`
- 不把个例当普遍规律
- 标出可迁移部分

### 未来预演

适合展示趋势、风险或战略选择。

标注为：

```text
类型：未来预演 / scenario
真实性：预测，不是事实
```

要求：

- 明确假设条件
- 不制造确定性
- 让读者看到“如果继续这样，会发生什么”

### 假设故事

适合解释概念、降低理解成本。

标注为：

```text
类型：假设故事
真实性：虚构，用于解释
```

要求：

- 不伪装成真实经历
- 场景要符合读者生活或业务处境
- 只服务一个概念

### 类比故事

适合把陌生机制解释成读者熟悉的机制。

要求：

- 说明相似点
- 说明类比边界
- 不用类比替代证据

### 反面案例

适合展示错误成本、失败机制、不要做什么。

要求：

- 不为了攻击而攻击
- 讲清楚失败机制
- 给出可迁移警示

### 微场景

适合短视频、小红书、开头、hook、过渡段。

要求：

- 一两个细节就够
- 不展开成长故事
- 直接服务读者识别和情绪

## 案例选择标准

优先选择同时满足这些条件的案例：

- 能直接支撑核心主张
- 读者能快速理解
- 细节具体
- 不需要大量背景解释
- 真实性边界清楚
- 符合作者声音
- 能放进目标平台长度
- 不抢走主张本身

## 案例输出格式

```text
主张：
案例类型：
真实性标注：
联网状态：
案例摘要：
关键细节：
承担功能：
为什么适合：
风险：
写入位置：
可用开头：
```

## 写入位置

- **开头**：用来抓注意力或制造场景。
- **论证中段**：用来解释机制或支撑主张。
- **转折处**：用来从抽象转入具体。
- **异议处理处**：用来回答读者反驳。
- **结尾**：用来形成记忆点或行动理由。

## 风险清单

- 虚构故事被写得像真实案例
- 真实事件没有核验
- 类比过度
- 案例比主张更抢戏
- 案例有趣但无功能
- 案例和目标读者无关
- 未来预演被写成确定预测
- 为了戏剧性擅自补事实
