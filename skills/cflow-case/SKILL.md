# CFlow 案例故事

## 边界

负责为内容寻找或设计“能支撑观点的案例/故事素材”。

案例默认服务表达效果。可以为了注意力、情绪、反差或记忆点加入故事；用户要求严谨论证时，再检查是否严格服务一个具体主张。

用户要求“真实故事、历史故事、生活细节、普通人能懂、有趣一点”时，先区分宏观制度案例和可写成场景的生活故事。信用制度、护照、公证、清算网络这类宏观案例只能解释机制；如果要做开头故事，优先找有人、动作、阻碍和具体物件的场景。故事进入正文前，不要急着把它抽象成概念。

故事开头硬检查：如果案例要承担正文开头，必须先检查是否有人、动作、阻碍、具体物件和现场顺序。前 120 字内默认不急着写“本质、核心、基础设施、验证层、复杂事实、可验证凭证”等抽象词；除非用户明确要求技术开门见山。

## 工作流

1. **确定主张**：先明确案例要支撑什么观点、机制、情绪或转化动作。
2. **选择案例类型**：真实事件、个人经历、客户案例、行业案例、历史生活场景、宏观制度案例、未来预演、假设故事、类比故事、反面案例或微场景。
3. **选择呈现方式**：默认先判断案例如何制造画面、情绪、反差、记忆点或转化桥；如果用户要的是故事开头，必须能写出人、动作、阻碍、物件和现场顺序。用户要求严谨时再标注真实性。
4. **筛选功能**：判断案例承担的是解释、趣味、情绪、反差、记忆点、异议处理、转化桥还是证明。
5. **生成候选**：给出多个不同策略的案例方向。
6. **评估表现力**：检查是否有画面、有反差、有情绪、有记忆点。只有用户要求严谨、真实、来源或合规时，才评估真实性边界。
7. **交接生产**：需要写进正文时交给 `$cflow-draft`；需要角度化时交给 `$cflow-angle`；需要营销转化时交给 `$cflow-marketing`。

## 输出

返回：

- 要支撑的主张
- 推荐案例类型
- 案例候选
- 呈现方式
- 案例功能
- 为什么适合
- 可继续加压的方向
- 写入正文的建议位置

## 严谨模式

用户明确要求真实、核查、来源、引用、合规或严肃论证时，再执行真实性规则：

- 真实历史事件写成确定事实时，标注“需要核验”或使用用户提供的可靠来源。
- 未联网时，历史故事只使用用户提供素材或常识级事实；涉及具体年份、人物、机构、政策细节和因果判断时，标注“需要核验”，不要为了故事效果补细节。
- 当前行业信息、公司人物细节或数据判断交给 `$cflow-research`。
- 虚构、假设、未来预演和类比需要标注类型（仅严谨模式必需）。
- 用户个人经历不擅自补关键事实。
