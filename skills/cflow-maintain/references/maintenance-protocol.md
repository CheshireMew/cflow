# 维护协议

## 输入分类

如果用户输入是一篇文章、账号拆解、课程笔记、反馈合集、转录或长素材，先做复合输入解析。不要先问“这整段属于哪个 skill”，而要把它拆成多个信息单元，再逐项分类、分析和收口。

常见信息单元：

- **写作技巧**：结构、开头、表达、节奏、论证、案例、标题、hook 或短内容推进方式。
- **用户自己的账号资料**：账号定位、主页表达、栏目、发布频率、受众、内容资产、表现数据、评论反馈或转化路径。
- **外部对标账号资料**：别人账号的人设、栏目、发布节奏、爆款样本、内容结构或可迁移模式。
- **引流方式**：私信、评论区、主页、链接、群、资料包、预约、表单或其他 lead capture 路径。
- **转化技巧**：offer、CTA、funnel stage、异议处理、信任铺垫、销售页面或成交动作。
- **事实资料**：数据、来源、事件、人物、产品功能、政策、平台规则或需要核查的信息。
- **作者偏好**：口癖、表达禁区、价值判断、个人经历、业务资产或私有背景。
- **发布环境观察**：平台、媒介、篇幅、审核、比例、入口、算法或短期表现经验。
- **案例和测试样本**：能验证规则是否执行的具体输入、输出或失败现场。
- **维护请求**：关于 skill 边界、路由、规则归属、重构、删除或校验的要求。

每个信息单元都要给出：

```text
信息类型：
写作或维护价值：
主要归属：
处理动作：
是否进入通用规则：
```

只有拆分后仍指向同一个根行为，才可以合并处理。不同维度不得因为来自同一篇文章就被压成单一规则、单一 skill 或单一结论。

把用户提供的每一项归类为：

- **规则**：会长期约束行为的指令。
- **流程步骤**：可重复执行的动作序列。
- **决策标准**：用于在选项之间做选择的判断。
- **发布环境笔记**：用户明确提到的发布位置、字数、链接、审核、比例、媒介或入口限制。
- **声音准则**：关于保留或塑造作者声音的说明。
- **写作机制**：能提升注意力、理解、信任、情绪、记忆、行动、作者声音或内容复用效率的内容生产规律。
- **缺陷报告**：使用 CFlow skill 时观察到的失败。
- **测试用例**：可用于验证行为的真实例子。
- **删除请求**：应该移除的规则或资源。
- **skill 系统架构请求**：skill 边界、路由、命名、目录结构或直接服务 skill 生命周期的工具链变化。

## 作者画像归属审计

维护反馈经常混合了通用流程缺陷和用户个人写法偏好。先分桶，再决定修改位置：

```text
通用规则：
作者画像：
单篇 brief：
候选证据：
拒绝沉淀：
```

判断标准：

- 能跨用户成立，且描述的是工具、流程、权限、路由、校验或 skill 边界 -> 通用规则，进入 `skills/`。
- 只描述这个用户怎样表达、讨厌什么、偏好什么节奏、哪些词不像本人 -> 作者画像，交给 `cflow-voice` 写入唯一 `profiles/voice-profile.md`。
- 只服务当前文章、当前项目、当前选题、当前客户或当前素材 -> 单篇 brief，不进通用 skill，也不进核心画像。
- 只出现一次，但可能反映作者偏好 -> 候选证据，交给 `cflow-voice` 写入候选证据。
- 只是执行失误、已有规则未执行、一次性情绪或不能泛化的信息 -> 拒绝沉淀。

禁止：

- 把“我讨厌这个词、这个不像我、以后别这样写”直接写成通用 skill 规则。
- 把“draft/edit/maintain 应该怎么工作”写进 `profiles/voice-profile.md`。
- 把单篇文章的工具名、标题、API 细节、当前角度写进 voice 核心画像。
- 为不同题材创建多个 voice profile。

用户亲自修订稿是高优先级证据。遇到“我改了一下、我稍微修改了、这样写才对、参考我这个版本”，或用户亲自修改标题、hook、opening、CTA、短发布文案时，不要只把它当新草稿；要比较用户修订方向：

- 哪些 AI 整理腔被删掉？
- 哪些用户口语、短句、吐槽被保留或新增？
- 哪些主题被降级为“小发现”，没有继续升维？
- 哪些结尾、CTA、解释和风险边界被压缩？
- 如果是包装资产：用户加了什么、删了什么，张力从哪里变强，哪些词更贴作者声音？

比较结果再分桶：可跨用户成立的进入通用规则；包装机制进入 `cflow-package`；只体现用户表达偏好的交给 `cflow-voice`；只服务当前文章的进入单篇 brief；一次性信息拒绝沉淀。

## 写作价值识别

`$cflow-maintain` 不直接沉淀写作技法，但必须先看见写作技法，再决定归属和迁移。面对写作方法论、对标材料、用户反馈或内容表现材料时，先问：

```text
它让写作变好的机制是什么？
它改善的是注意力、理解、信任、情绪、记忆、行动、作者声音，还是内容复用效率？
它对应哪个内容能力层：选题、角度、结构、hook、短内容、声音、转化、视觉、传播、SEO、案例或复盘？
它是长期规则、执行检查项、例子，还是只适合作为测试用例？
```

识别后再进入归属判断。不要把“写作内容细节不属于 maintain”误解成“不需要分析写作效果”。`cflow-maintain` 的职责是把写作价值翻译成正确 skill 的长期规则，而不是只维护流程和约束。

### 专项分析委托

`cflow-maintain` 不直接替代专项 skill 做完整内容分析。它负责判断是否需要分析、调用哪个能力边界、以及分析结果是否值得沉淀为 skill 规则。

当信息单元需要专项判断时，先按下列方向委托分析，再回到 `cflow-maintain` 收口：

| 信息单元 | 先交给 | 回到 maintain 后判断 |
|---|---|---|
| 用户自己的账号资料、主页、栏目、表现数据 | `cflow-account` | 是否是账号资产、诊断假设、生产系统规则或测试用例 |
| 外部对标账号、栏目、爆款样本、发布节奏 | `cflow-benchmark` | 是否是可迁移模式、对标资产、例子或测试用例 |
| 引流方式、offer、CTA、转化路径 | `cflow-marketing` | 是否形成通用转化规则，或只是业务资产 / 私有配置 |
| 标题、hook、opening、CTA 文案技巧 | `cflow-package` | 是否应进入包装规则、例子或测试用例 |
| 短内容结构、短脚本、短链路推进 | `cflow-shortform` | 是否应进入短内容规则或拆条方法 |
| 主张、矛盾、读者张力 | `cflow-angle` | 是否应进入角度规则 |
| 长文结构、完整草稿推进 | `cflow-draft` | 是否应进入成稿规则 |
| 事实、来源、当前平台信息 | `cflow-research` | 是否需要来源约束、核查规则或拒绝沉淀 |
| 作者偏好、表达禁区、个人风格 | `cflow-voice` | 是否进入唯一 `profiles/voice-profile.md`，而不是通用规则 |
| 发布后指标、评论和反馈 | `cflow-review` | 是否形成复盘规则、资产卡片或测试假设 |

委托分析不是把维护权交出去。专项 skill 只负责识别机制、边界和可迁移性；是否新增、合并、移动、删除、分流或拒绝沉淀，仍由 `cflow-maintain` 决定。

常见写作价值映射：

| 改善对象 | 可能归属 |
|---|---|
| 读者痛点、选题来源、内容栏目 | `cflow-topic` |
| 账号定位、主页承诺、栏目组合、账号数据反馈、转化路径优先级 | `cflow-account` |
| 主张、矛盾、读者张力、premise | `cflow-angle` |
| 长文结构、题材结构、完整草稿推进 | `cflow-draft` |
| 首句、标题、hook、开头、CTA 文案 | `cflow-package` |
| 超短、短内容、短脚本、短发布文案、长文拆短 | `cflow-shortform` |
| 作者声音、AI 味、表达禁区 | `cflow-voice` |
| offer、funnel、转化桥、行动路径 | `cflow-marketing` |
| 封面、插图、视觉隐喻、视听留存 | `cflow-image` |
| 分享动机、截图点、传播单元 | `cflow-viral` |
| 搜索意图、AI 可引用结构 | `cflow-seo` |
| 案例、故事、类比、证明动作 | `cflow-case` |
| 发布后指标和反馈学习 | `cflow-review` |

## 归属判断

把每项内容放到最窄、最耐用的边界。

- 统筹、套件路由、任务编排和能力层拆解放 `cflow`。
- 写作前采访、讨论、追问缺失信息、素材盘点和 content brief 构建放 `cflow-brief`。
- 资料搜寻、事实核查、来源评估、证据包和引用整理放 `cflow-research`。
- 发现和评分放 `cflow-topic`。
- 内容对标、账号拆解、爆款结构拆解和 copywork 颗粒度检查放 `cflow-benchmark`。
- 用户自己账号的定位、主页表达、栏目组合、账号数据反馈、转化路径和生产系统诊断放 `cflow-account`。
- 分享动机、传播单元、二创入口、截图传播和病毒式传播复盘放 `cflow-viral`。
- SEO/GEO/AEO/LLMO、搜索意图、关键词、主题集群和 AI 可引用结构放 `cflow-seo`。
- 案例故事、真实性标注、未来预演、假设故事和支撑性例子放 `cflow-case`。
- 主张和读者张力放 `cflow-angle`。
- 从结构到草稿的指导放 `cflow-draft`。
- 超短、短内容、短脚本、短发布文案、短内容系列和长文拆短放 `cflow-shortform`。
- 修改诊断和声音保留放 `cflow-edit`。
- 作者声音画像、写作人格、灵魂倾向和表达禁区放 `cflow-voice`。
- 硬广/软广、offer、CTA 强度、funnel stage 和转化路径放 `cflow-marketing`。
- 标题、hook、开头、CTA 和短发布文案放 `cflow-package`。
- 封面、插图、配图、文章头图、thumbnail text、cover text、视觉 brief 和图片 prompt 放 `cflow-image`。
- 表现学习和下一次实验放 `cflow-review`。
- 维护流程放 `cflow-maintain`。

## 源码布局

`$cflow-maintain` 维护的是 CFlow skill 系统，不是整个项目。只有直接服务 skill 生命周期的文件才进入维护范围。

允许处理：

- `skills/` 真源里的 skill 规则、reference 和 agent metadata。
- skill 路由、规则归属、边界、命名和目录结构。
- 直接服务 skill 生命周期的 schema、校验脚本、registry/sync 脚本、测试和 README 相关段落。

排除处理：

- 个人复盘资产、截图、指标、评论、私有案例和普通内容产物。
- 普通 Git hygiene、环境配置、应用代码或与 skill 生命周期无关的仓库工程。
- 用户没有明确纳入维护计划的项目文件。

唯一可编辑真源是当前仓库：

```text
<repo-root>/
└── skills/
    ├── cflow/
    ├── cflow-brief/
    ├── cflow-research/
    ├── cflow-topic/
    ├── cflow-benchmark/
    ├── cflow-account/
    ├── cflow-viral/
    ├── cflow-seo/
    ├── cflow-case/
    ├── cflow-angle/
    ├── cflow-draft/
    ├── cflow-shortform/
    ├── cflow-edit/
    ├── cflow-voice/
    ├── cflow-marketing/
    ├── cflow-package/
    ├── cflow-review/
    └── cflow-maintain/
```

`$HOME\.codex\skills` 下可以有 Codex 发现链接，但不要通过链接编辑。修改当前仓库中的源码，然后校验并提交。其他 AI Agent 或 AI 工具可以按自己的插件、工具、skills 或 prompt 发现机制兼容 CFlow 的 `skills/` 真源。

创建、删除或重命名 skill 后，必须同步 Codex 个人 skill 发现入口：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/sync_personal_skills.ps1 -PruneStale
```

同步脚本只创建缺失 junction，并且只删除 stale 的 CFlow junction：名字是 `cflow*`、类型是 junction、target 指向本仓库 `skills`、且 target 已不存在。不得手动复制 skill 到个人目录，也不得通过个人目录编辑 skill。

如果一条规则似乎适合多个 skill，先判断根行为。只添加一个主要规则；只有路由需要时才在其他 skill 加短提示。

## 反膨胀原则

维护默认不是加规则。每次看到有价值输入时，先做减法审计，再决定是否新增。

新增前必须依次检查：

1. **已覆盖**：现有规则是否已经能处理，只是执行时没遵守？
2. **可收紧**：能否改一条已有规则，而不是再加一条平行规则？
3. **可合并**：是否有重复或相邻规则可以合成一个更清楚的规则？
4. **可移动**：是否只是规则放错位置，应该迁移而不是复制？
5. **可删除**：是否有旧规则因为这次重构变得过时、重复或误导？
6. **可作为例子**：是否只是帮助理解规则的案例，不需要进入长期规则？
7. **可作为测试用例**：是否只暴露执行失败，应进入测试或示例，而不是扩写规则？
8. **可分流**：是否属于作者 profile、业务资产、发布环境短期经验或私有素材，不该写进通用 skill？
9. **可拒绝沉淀**：是否只是一次性偏好、噪音、未验证猜测或过窄场景？

只有上面都不成立，才新增规则。新增规则必须说明它替代、合并或强化了什么；如果只是净增加，必须说明收益为什么大于维护成本。

## 特殊情况分流

这些输入不要直接写进通用 skill：

| 输入类型 | 默认处理 |
|---|---|
| 单次失败案例 | 作为测试用例、例子或执行提醒；先查已有规则是否未执行 |
| 作者个人偏好、口癖、禁用词 | 进入 `cflow-voice` 的唯一 `profiles/voice-profile.md`，不写成通用写作规则 |
| 特定业务链接、CTA、资产、产品入口 | 进入用户资产、profile 或专项 leadgen 配置，不写成通用规则 |
| 发布环境短期经验、热点、临时算法观察 | 作为发布环境笔记、review 经验或测试假设，不写成长期规则 |
| 外部方法论整包 | 先拆成机制、例子和不可迁移部分，不能整包入库 |
| 执行失败但规则已存在 | 标记为已有规则未执行，必要时补测试，不新增重复规则 |
| 只对一个行业、账号、产品成立的细节 | 作为例子或私有配置，除非同类替换后仍成立 |

分流不是忽略。分流后要说明它去了哪里、为什么不进入通用 skill、以后什么条件下才重新评估。

## 语料型 skill 维护

维护含原始语料、作者风格、对标样本、案例库、训练数据、评估集、合成样本或生成脚本的 skill 时，先做资源分层，再判断规则变更。不要把所有文件都当成同等可信的规则来源。

资源分层顺序：

1. **原始语料**：用户提供的原文、真实案例、真实输出、可核验样本或采集数据。
2. **人工蒸馏**：基于原始语料整理出的风格剖面、模式说明、使用指南或 reference。
3. **派生训练 / 评估样本**：为了 SFT、RAG、测试或 few-shot 生成的 instruction、input、output。
4. **合成样本**：由模型或脚本扩写、改写、补全的样本。
5. **生成脚本**：会持续产出样本、模板或候选输出的 helper。
6. **测试输出**：用于验证 skill 行为的代表性结果。

原始语料与人工蒸馏、训练数据、合成样本或生成脚本冲突时，以原始语料为真源。派生资源只能在证明不污染行为时保留；如果它们持续诱发错误输出，应删除、重建或降级为明确标注的测试材料，不保留兼容层。

写作、风格、作者声音、对标模仿类 skill 的校验，不能只看 frontmatter、schema、脚本是否运行或 JSON 是否可解析。必须抽取代表性输入生成输出，并与原始语料做形态对照，至少检查：

- 输出篇幅和段落是否接近原语料。
- 是否引入原语料没有的结构形态，例如报告、清单、标题、总结或模板句。
- 是否保留了可迁移机制，同时没有把方法论显性写成分析框架。
- 是否新增了原始素材不支持的事实、身份、经历、承诺或来源。

做通用化时，先分清“可迁移方法”和“不可迁移表达”。方法论可以抽象到其他行业或场景，但输出形态必须回到原始样本支持的表达方式。不要为了通用化，把短内容、口吻、作者声音或平台语境改成中立报告、咨询框架或 AI 总结。

如果旧训练集、合成样本、生成脚本或参考文件已经成为错误行为来源，应把它们视为旧架构的一部分处理。重构完成后不要保留旧 helper、旧派生样本、旧模板或旧恢复路径。

## 缺陷归因

处理缺陷报告时，先命名根行为，不要按表面场景直接写规则。

常见根行为包括：

- **已有规则未执行**：skill 已经覆盖，但输出没有遵守。
- **规则缺失**：现有 skill 没有可执行约束。
- **写作机制未识别**：维护时只看到流程、归属或约束，没有先提炼输入里能改善内容效果的机制。
- **只增不删**：每次维护都追加规则，没有审计能否合并、移动、删除或拒绝沉淀。
- **特殊案例通用化**：把一次性案例、作者偏好、业务资产或发布环境短期经验写成通用规则。
- **路由缺失**：任务应进入另一个 skill，但入口没有触发。
- **边界冲突**：多个 skill 对同一行为给出不同方向。
- **素材越界**：输出新增了用户素材没有支撑的事实、功能、承诺、服务或运营范围。
- **测试用例不足**：规则存在，但缺少能暴露失败的真实样例。

只有确认根行为后，才决定新增、收紧、移动、删除规则或补测试用例。不能把执行失败自动当作 skill 缺规则。

## 泛化检查

从失败案例提炼规则时，禁止把案例里的具体发布环境、交付形态、对象、行业或文案场景直接固化为触发条件。

先做同类替换测试：

```text
把案例中的发布环境、交付形态、对象、行业或具体素材替换成同类变量后，这条规则是否仍成立？
```

如果仍成立，规则必须写成可迁移约束；具体案例只能作为测试用例或例子。

例子：

```text
不够好：群简介 / bio / 置顶简介改写时，不得新增原文没有的群功能。
更好：用户提供明确原始素材时，改写、包装、营销强化都不得新增未被素材支撑的事实、功能、承诺、服务或运营范围；如果转化需要补信息，必须标注为建议补充，而不是混进成稿。
```

维护计划里要分清：

- **长期规则**：可迁移到多个同类场景的行为约束。
- **测试用例**：这次暴露失败的具体素材和场景。
- **例子**：帮助理解规则，但不作为唯一触发条件。

## 语言规则

CFlow 使用中文作为唯一正文真源：

- `SKILL.md` 和 `references/` 用中文写规则。
- `name` 保持英文技术名。
- `description` 用中文描述，同时保留必要英文触发关键词。
- `agents/openai.yaml` 的展示文案用中文。
- 不维护中英双语全文，不创建平行 `zh` / `en` 真源。
- 如果未来需要英文版，作为独立导出版生成。

## 覆盖状态

使用这些标签：

- **已覆盖**：不用改。
- **部分覆盖**：收紧或扩展现有规则。
- **重复**：合并到最佳位置并删除重复。
- **冲突**：选择符合 CFlow 边界的规则；业务意图不清时问用户。
- **新规则**：添加到最窄 skill 或 reference。
- **过时**：不再符合架构时删除。
- **应分流**：不进通用规则，转为 profile、用户资产、发布环境笔记、review 经验、例子或测试用例。
- **拒绝沉淀**：过窄、未验证、一次性偏好或维护成本高于收益，不写入 skill。

## 重构规则

- 每条规则只保留一个事实源。
- 迁移后不要保留旧 helper、旧流程或兼容解释。
- 优先移动规则，不复制规则。
- 优先合并和替换，不叠加相邻规则。
- 大改时优先追求净减少、净合并或净清晰；净新增必须说明收益大于维护成本。
- 特殊案例必须先分流；只有同类替换后仍成立，才进入长期规则。
- 不把 profile、用户资产、业务配置、发布环境短期经验写成通用 skill 规则。
- `SKILL.md` 保持精简，详细模式放 `references/`。
- 只有套件边界、编排规则或协作调度变化时才更新 `cflow`。
- 规则真源归属和任务执行协作不是一回事。每条规则只保留一个主要归属，是为了避免知识库漂移；一次用户任务可以由多个 skills 串联、并行或回跳协作完成。
- 只有展示 metadata 过时时才更新 `agents/openai.yaml`。

## 维护反模式

- **过早治理化**：面对写作方法论或内容反馈时，只讨论流程、边界、归属、去重和校验，没有先说明这条输入为什么能让内容更有效。
- **技法留在 maintain**：已经识别出具体写作机制，却把规则写在 `cflow-maintain`，导致专项 skill 调用不到。
- **只看安全边界**：只问是否越界、是否重复、是否需要核查，却不问它改善了读者注意力、理解、信任或行动中的哪一环。
- **只增不删**：维护结果总是新增段落，没有删除、合并、移动或拒绝任何内容。
- **规则堆叠替代重构**：已有规则表达不清时继续补丁式加规则，而不是重写成一个更清楚的规则。
- **特殊案例通用化**：把单次案例、发布环境短期经验、作者偏好或业务资产变成所有任务都要遵守的规则。
- **把 profile 当 skill 规则**：把某个作者、产品、社群、渠道或业务的私有信息写进通用 skill。
- **外部方法论照单全收**：把某个创作者、课程或框架整包搬进 CFlow，而不是拆成可迁移机制和不可迁移部分。

## 审批标准

用户必须批准：

- 受影响 skill 或直接服务 skill 生命周期的文件
- 要编辑的文件
- 要新增、移动、合并或删除的规则
- 要拒绝沉淀或分流处理的内容
- 预计净体积影响：净增加、净减少、替换或合并
- 校验计划
- 提交计划

如果用户修改计划，先重写计划并再次请求批准。

## 校验

运行：

```powershell
python scripts\quick_validate.py
```

校验所有变更 skill。只要套件路由、所有权边界或共享约定变化，就校验全部 CFlow skills。

如果创建、删除或重命名了 skill，同步个人 skill 链接后再校验一次：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\sync_personal_skills.ps1 -PruneStale
python scripts\quick_validate.py
```

## 提交

只有用户明确要求提交，或批准计划包含提交时，才在校验通过后提交。commit message 保持聚焦：

- `Update <skill> <rule-area>`
- `Move <rule> into <skill>`
- `Refine CFlow routing`
- `Remove duplicate <rule-area> guidance`
- `Localize CFlow skills to Chinese source`

如果同一次维护计划同时改了 skill 规则和 skill 生命周期工具链，提交说明要覆盖完整维护范围；不把普通项目维护混进本 skill 的提交计划。
