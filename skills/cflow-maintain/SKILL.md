# CFlow Maintain

## 真源

唯一可编辑真源是当前仓库根目录下的 `skills/`。`$HOME\.codex\skills\cflow-*` 只是 Codex 发现用的链接，不是编辑入口。

## 文档标准

硬规则：

- 正文不要重复 frontmatter `description` 已经说清的范围。
- 只写这个 skill 负责的事；不要写大段“不负责”清单。
- 不写交接规则。跨 skill 调度由 `cflow` 主入口负责。
- 能归类的规则必须归类，避免同一意思散落在多个段落。
- 交付物只保留核心形态。别把同义词、子场景、扩展用途都列成独立交付物。
- 工作流保留关键判断和关键动作，通常 3 到 5 步足够。
- 模板只保留能直接指导输出的骨架，不保留解释性口号、术语堆叠或自我说明。
- 质量闸门只保留会改变结果的检查项；删除泛泛正确但无法执行的句子。
- 回归样例只放最容易失败、最能约束行为的少数样例。
- 文档越长，越要优先删重复、合并近义规则、删除边界说明，而不是继续补丁。
- 检查规则是否被单个案例、领域、平台、作者或素材来源过拟合；能抽象成底层动作时，不保留领域限定。
- 失败用例、追问协议、质量闸门和反模式清单只要会改变执行行为，就不能因为“太长”或“看起来重复”直接删除；必须先等效合并到更窄位置，或明确归档为测试用例 / 内容资产。

## 硬门槛

在用户明确批准具体更新计划前，禁止修改任何 CFlow skill 文件。

批准前允许：

- 读取 CFlow skill 文件。
- 检查重复、冲突、过时规则、旧 helper、旧导出和旧恢复逻辑。
- 判断唯一事实源。
- 提出治理和重构计划。

批准前禁止：

- 修改 `SKILL.md` 或其他 skill 规则文件。
- 删除、移动、合并文件。
- 提交 commit。
- 重新生成 metadata。
- 运行会改变工作区的同步脚本。

执行治理时禁止：

- 创建新的外部规则文件，或把新规则下沉到不会被调用的位置。
- 保留双真源、兼容层、旧 helper、旧流程、旧导出或旧恢复逻辑。
- 把应当 always-on 生效的执行规则放在不会被当前任务读取的位置。
- 用新增规则堆叠掩盖旧规则归属错误。

## 核心原则

按根因收口，不按现象修补。先确定单一来源，再一次性迁移所有调用点。确保原功能完整迁移后，禁止保留兼容层、旧类型、旧 helper、旧恢复逻辑、旧导出和旧解释。不要停在半迁移状态。

治理生产型 skill 时，默认保护三项优先级：

1. **不要 AI 味**：最高优先级。不能为了模板、传播、营销、SEO 或效率牺牲作者判断、素材边界和非模板化表达。
2. **写作模板**：模板必须是可迁移结构、信息顺序或检查动作，不是固定句式、固定段落、固定腔调或平台口头禅。
3. **传播度**：默认保护截图点、复述句、分享动机和承接路径；传播加压不能制造空情绪、爆款模板腔、事实夸大或作者声音失真。

治理优先级：

- 先识别会改变执行行为的规则。
- 再删重复和废话。
- 再归类相近规则。
- 再收紧工作流。
- 再做反过拟合检查。
- 最后才新增缺失规则。

## 工作流

1. **锁定文件**：确认要改哪些 `SKILL.md`、metadata、脚本或测试。
2. **行为保真审计**：先标出会改变执行行为的规则，包括失败用例、追问协议、质量闸门、反模式、默认模式、输出协议和路由防线。
3. **删减归类**：删除重复 description 的正文、删掉无行为价值的边界说明、合并近义规则；被删行为规则必须已等效合并、移动或归档。
4. **收紧主流程**：保留核心交付物、核心工作流、必要模板和质量闸门。
5. **反过拟合**：把案例、领域、平台、作者和素材来源替换成变量，确认保留的是底层动作。
6. **补最少规则**：只有现有规则无法覆盖失败根因时，才补少量规则或回归样例。
7. **校验**：运行 `python scripts\quick_validate.py`。

## 审批计划格式

编辑前返回中文计划，只展示有内容的项。不要输出空字段。校验、同步和提交只在会实际发生时说明；用户没要求提交时不要展示提交计划。

```text
这次要治理什么：
根因判断：
涉及文件：
需要删减 / 归类 / 收紧的内容：
需要保留的唯一真源：
风险或不确定点：
确认后我会修改文件并跑校验。
```

计划后必须请求明确批准。模糊同意不算批准；等待用户清楚表示同意后才能执行。

## 运行失败审计

当输入是一整段 CFlow 使用失败现场或连续纠偏对话时，审计执行链路，不复盘某条内容本身。

先按时间线标出：

```text
用户原始任务：
用户点名的 skill：
真实内容对象：
期望交付形态：
第一次误读发生在哪里：
第一次纠偏说了什么：
系统是否重判任务对象、执行协议和交付形态：
后续是否继续沿用错误策略：
最终用户认可的版本或判断：
```

再定位断点类型：

- **对象错置**：把用户点名的 skill、工具、文件或协议当成正文对象。
- **协议失效**：用户点名某个 skill，但系统没有执行其质量门槛。
- **默认能力缺失**：某个 skill 没有完成自己职责内的基础能力。
- **过度展开**：小任务被重型流程、过多文档读取或过多规则检查带偏。
- **纠偏未重判**：用户已经指出“不是这个”，系统仍在旧理解上改句子。
- **规则已存在未执行**：已有规则没有被执行。
- **规则放错层级**：规则放在不会被调用的位置，导致实际无效。
- **行为约束误删**：治理时把会改变执行行为的失败用例、追问协议、质量闸门或反模式当成重复内容删除，导致 skill 能力降级。
- **旧架构残留**：旧 reference、旧 helper、旧导出、旧恢复逻辑或兼容解释仍在影响行为。

审计输出必须包含：

```text
根断点：
暴露的文档问题：
需要删减 / 归类 / 收紧的内容：
可作为测试用例的用户原话：
```

## 规则归属

每条规则只能有一个主要真源。

- 专项生产规则放在对应专项 `SKILL.md`。
- 作者表达偏好放在 `profiles/voice-profile.md`。
- 内容资产放在 `profiles/content-assets/`。
- metadata 只维护展示信息，不承载行为规则。
- 运行时必须稳定生效的规则，必须进入实际会被调用的 `SKILL.md`。

## 内置规则迁移

外部 reference、旧跨文件规则、旧 helper 和旧恢复逻辑都不能继续作为运行依赖。

迁移判断：

- 仍有价值的规则，迁移到实际需要它的专项 skill。
- 迁移后 `SKILL.md` 是唯一运行入口，旧外部规则文件删除或保持已删除状态。
- 回归样例放在最容易失败的专项 skill，不放进跨文件说明。
- 如果某条规则连续失效，优先收紧本地工作流、质量闸门或回归样例。

## 覆盖状态

审计规则时使用这些标签：

- **已覆盖**：当前唯一真源已经覆盖，不用改。
- **已等效合并**：原规则的行为效果已被更窄、更清晰的位置覆盖，可以删除旧表述。
- **应保留**：虽然看起来像例子、长表或反模式，但它会改变执行行为，必须保留或压缩后保留。
- **部分覆盖**：已有规则方向对，但需要收紧、扩展或移到更清晰位置。
- **重复**：多个位置表达同一规则，合并到最佳位置并删除重复。
- **冲突**：规则互相矛盾，选择符合用户目标的版本；业务意图不清时问用户。
- **新规则**：当前没有覆盖，添加到最窄真源。
- **过时**：不再符合当前架构，删除。
- **应移动**：规则有价值，但放错文件。
- **应删除**：规则无效、误导、重复或属于旧架构。
- **应归档**：不进 skill 主规则，归入 profile、内容资产、发布环境笔记、review 经验、例子或测试用例。
- **行为误删风险**：准备删除的规则承载了具体失败防线、追问动作、输出协议或质量门槛，必须先改为应保留、已等效合并、应移动或应归档。

## 反膨胀审计

修改前先检查是否能删除、合并或收紧。不要默认新增。

净减少不是目标本身。大改必须同时满足净清晰和能力不降级；如果删掉一条规则会让 skill 少做一个判断、少问一个关键问题、少挡一个常见失败或少执行一个质量闸门，就不是合格删减。

新增前依次检查：

1. 现有规则是否已经覆盖，只是执行时没遵守。
2. 是否能收紧一条已有规则，而不是新增平行规则。
3. 是否能合并相邻规则。
4. 是否应移动到另一个真源。
5. 被删规则是否已经等效合并，还是存在行为误删风险。
6. 是否有旧规则因为这次变更需要删除。
7. 是否只是例子、测试用例或生产资产，不应成为长期规则。
8. 是否属于作者画像、业务资产、发布环境短期经验或私有素材。

只有上面都不成立，才新增长期规则。大改时追求净减少、净合并或净清晰。

## 语料型 skill 治理

维护含原始语料、作者风格、对标样本、案例库、训练数据、评估集、合成样本或生成脚本的 skill 时，先做资源分层。

资源可信顺序：

1. 原始语料。
2. 人工蒸馏。
3. 派生训练 / 评估样本。
4. 合成样本。
5. 生成脚本。
6. 测试输出。

治理规则：

- 原始语料与人工蒸馏、训练数据、合成样本或生成脚本冲突时，以原始语料为真源。
- 派生资源只能在证明不污染行为时保留。
- 如果旧训练集、合成样本、生成脚本或参考文件已经成为错误行为来源，应把它们视为旧架构的一部分处理。
- 重构完成后不要保留旧 helper、旧派生样本、旧模板或旧恢复路径。

## 重构规则

- 按根因收口，不按现象修补。
- 先确定单一来源，再迁移所有调用点。
- 迁移后不要保留旧 helper、旧流程、旧导出、兼容解释或旧恢复逻辑。
- 优先把原则规则移动到实际调用的 `SKILL.md`。
- 优先合并和替换，不叠加相邻规则。
- `SKILL.md` 是唯一规则入口；详细模式必须合并进主文件或删除，不能继续放在外部规则文件。
- 只有展示 metadata 过时时才更新 `agents/openai.yaml`。
- 删除、移动、重命名或改路由时，同时检查所有调用点，不留下旧引用。

## 发现入口同步

创建、删除或重命名 skill 后，必须同步 Codex 个人 skill 发现入口：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/sync_personal_skills.ps1 -PruneStale
```

同步脚本只创建缺失 junction，并且只删除 stale 的 CFlow junction：名字是 `cflow*`、类型是 junction、target 指向本仓库 `skills`、且 target 已不存在。

只修改现有 `SKILL.md` 内容、不创建 / 删除 / 重命名 skill 时，不运行同步脚本。

## 校验

默认运行：

```powershell
python scripts\quick_validate.py
```

需要额外校验的情况：

- 创建、删除或重命名 skill：先同步发现入口，再运行 quick validate。
- 修改 `agents/openai.yaml`：检查 metadata 是否仍只承载展示信息。
- 删除旧文件：检查 `rg` 不再能搜到旧路径、旧 helper、旧导出或旧恢复逻辑。

## 提交

只有用户明确要求提交，或批准计划包含提交时，才在校验通过后提交。commit message 保持聚焦：

- `Update <skill> governance`
- `Move <rule> into <skill>`
- `Remove duplicate <rule-area> guidance`
