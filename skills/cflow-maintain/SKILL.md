# CFlow Maintain

## 职责边界

`cflow-maintain` 是 CFlow skill 系统的治理维护工具。它负责审计、更新、重构和校验 CFlow skill 本身，不负责普通内容生产，也不负责从优质内容中提炼新生产机制。

唯一可编辑真源是当前仓库根目录下的 `skills/`。`$HOME\.codex\skills\cflow-*` 只是 Codex 发现用的链接，不是编辑入口。

允许处理：

- `skills/` 里的 `SKILL.md` 和 `agents/openai.yaml`。
- skill 路由、边界、命名、目录结构和发现入口。
- 规则归属、唯一事实源、重复、冲突、过时、误导和事实源分裂。
- 运行失败审计、误路由、过度展开、规则放错层级、连续纠偏失效和规则已存在但未执行。
- 旧外部规则文件、旧 helper、旧导出、旧恢复逻辑、旧流程和兼容层的清理、合并和删除。
- 直接服务 skill 生命周期的 schema、校验脚本、registry/sync 脚本、测试和 README 相关段落。

不负责：

- 从优质内容、外部方法论、样稿、课程笔记或对标拆解里主动提炼生产机制；这属于 `$cflow-absorb`。
- 写内容、改内容、做标题、成稿、包装、研究、复盘或发布前质检普通内容。
- 维护作者声音画像、账号私有资产、普通内容资产或个人 profile，除非它们被明确纳入治理计划。
- 普通项目工程、环境配置或与 CFlow skill 生命周期无关的文件。

## 与 cflow-absorb 的分工

- `$cflow-absorb`：识别内容生产机制，把新方法论、样稿、对标、课程笔记和内容失败反馈转成可迁移的生产能力升级方案。
- `$cflow-maintain`：治理 CFlow skill 系统，把明确要落地的升级方案合并到唯一事实源，并清掉旧结构、重复规则、冲突边界和运行失败根因。

如果用户的输入同时包含内容方法论和治理请求，先由 `$cflow-absorb` 判断哪些机制值得吸收；再由 `cflow-maintain` 判断怎么合并、移动、删除和校验。如果输入主要是在说 CFlow 执行错、路由错、规则无效、边界混乱、流程过重或旧架构残留，直接进入 `cflow-maintain`。

## 硬门槛

在用户明确批准具体更新计划前，禁止修改任何 CFlow skill 文件。

批准前允许：

- 读取 CFlow skill 文件。
- 检查重复、冲突、过时规则、旧 helper、旧导出和旧恢复逻辑。
- 判断唯一事实源和真实边界。
- 提出治理和重构计划。

批准前禁止：

- 修改 `SKILL.md` 或其他 skill 规则文件。
- 删除、移动、合并文件。
- 提交 commit。
- 重新生成 metadata。
- 运行会改变工作区的同步脚本。

执行治理时禁止：

- 创建新的外部规则文件，或把新规则下沉到不会被调用的位置。
- 保留双真源、兼容层、旧 helper、旧流程、旧导出或旧恢复逻辑。
- 把一个 skill 职责内必须具备的基础能力外包给另一个 skill。
- 把应当 always-on 生效的执行规则放在不会被当前任务读取的位置。
- 用新增规则堆叠掩盖旧规则归属错误。

## 核心原则

按根因收口，不按现象修补。先确定单一来源和唯一真实边界，再一次性迁移所有调用点。确保原功能完整迁移后，禁止保留兼容层、旧类型、旧 helper、旧恢复逻辑、旧导出和旧解释。不要停在半迁移状态。

每个 skill 必须承担自己职责内的完整能力。只有任务不属于该 skill 的职责，或者继续处理会改变上游合同，才交给别的 skill。

治理判断示例：

- 写作 / 成稿 skill 必须有自己的成稿质量闸门和反默认 AI 文体能力，不能要求用户额外点名 edit 才能避免 AI 味。
- 检测 / 改稿 skill 必须有自己的 AI 味诊断、结构诊断和最小改稿流程，不能把诊断责任推给 voice 或 check。
- 包装 skill 必须能自己判断标题、hook、开头和 CTA 的有效性；只有需要完整正文时才交给 draft。
- 研究 skill 必须能自己处理来源、事实状态和证据包；只有要写正文时才交给 draft。
- 入口 skill 只负责意图识别和最短路由，不承担生产正文、改稿、研究、包装或质检。

如果运行失败来自某个生产 skill 默认能力不足，优先修改该生产 skill 的本地规则、质量闸门或回归样例；不要要求用户下次手动追加另一个 skill 来补救。

## 工作流

1. **确认任务类型**：判断这是治理维护、运行失败审计、旧架构迁移、发现入口同步、校验修复，还是吸收进化。吸收进化交给 `$cflow-absorb`。
2. **锁定治理对象**：列出涉及的 skill 主文件、agent metadata、profile、脚本或旧文件，并确认哪些属于本次治理范围。
3. **定位唯一事实源**：判断每条规则应该由哪个 `SKILL.md` 或 profile 承担。旧外部规则只能作为待清理对象，不作为新规则承载层。
4. **审计边界和能力**：检查是否存在职责错位、过度路由、默认能力缺失、规则放错层级、旧跨文件规则残留或双真源。
5. **检测规则状态**：标记已覆盖、部分覆盖、重复、冲突、过时、应移动、应删除、应分流或新规则。
6. **选择治理动作**：合并、移动、删除、收紧、拆分、重命名、同步发现入口、补校验或补回归样例。
7. **做反膨胀审计**：先看能否收紧、合并、移动或删除旧规则；只有确实需要时才新增长期规则。
8. **请求批准**：给出具体治理计划，等待用户明确批准。
9. **应用变更**：只修改批准范围内的文件。原则规则属于别处就移动，不复制；能替换旧规则就不叠加新规则。
10. **同步发现入口**：只有创建、删除或重命名 skill 时，运行 `powershell -ExecutionPolicy Bypass -File scripts/sync_personal_skills.ps1 -PruneStale`。
11. **校验**：运行 `python scripts\quick_validate.py`。如果改动了路由、边界、skill 列表或共享约定，校验全部 CFlow skills。
12. **提交**：只有用户明确要求提交，或批准计划包含提交时，才在校验通过后提交。

## 审批计划格式

编辑前返回中文计划，只展示有内容的项。不要输出空字段。校验、同步和提交只在会实际发生时说明；用户没要求提交时不要展示提交计划。

```text
这次要治理什么：
根因判断：
涉及文件：
需要合并 / 移动 / 删除的规则：
需要保留的唯一真源：
会删除哪些旧结构：
风险或不确定点：
确认后我会修改文件并跑校验。
```

计划后必须请求明确批准。模糊同意不算批准；等待用户清楚表示同意后才能执行。

## 运行失败审计

当输入是一整段 CFlow 使用失败现场或连续纠偏对话时，审计执行链路，不复盘某条内容本身。

先按时间线标出：

```text
用户原始任务：
用户点名的 skill：
真实内容对象：
期望交付形态：
第一次误读发生在哪里：
第一次纠偏说了什么：
系统是否重判任务对象、执行协议和交付形态：
后续是否继续沿用错误策略：
最终用户认可的版本或判断：
```

再定位断点类型：

- **对象错置**：把用户点名的 skill、工具、文件或协议当成正文对象。
- **协议失效**：用户点名某个 skill，但系统没有执行其质量门槛。
- **默认能力缺失**：某个 skill 没有完成自己职责内的基础能力。
- **过度展开**：小任务被重型流程、过多文档读取或过多规则检查带偏。
- **过度路由**：当前 skill 本该解决的问题被转给别的 skill。
- **纠偏未重判**：用户已经指出“不是这个”，系统仍在旧理解上改句子。
- **规则已存在未执行**：已有规则没有被执行。
- **规则放错层级**：规则放在不会被调用的位置，导致实际无效。
- **边界混乱**：入口、生产 skill、维护 skill 或吸收 skill 之间职责不清。
- **旧架构残留**：旧 reference、旧 helper、旧导出、旧恢复逻辑或兼容解释仍在影响行为。

审计输出必须包含：

```text
根断点：
不是哪类问题：
暴露的缺失规则：
应该升级的 skill：
是否需要修改入口判断：
是否需要修改该 skill 的默认质量门槛：
是否需要删除、移动或合并旧规则：
可作为测试用例的用户原话：
```

审计时必须区分两件事：

- **能力缺失**：某个 skill 在自己职责内没有完整能力，应补该 skill。
- **职责越界**：用户要的不是该 skill 的任务，应交给正确 skill。

不要把能力缺失误判成职责越界。比如 draft 写出来有默认 AI 文体，是 draft 成稿质量门槛缺失；不是要求用户下次先跑 edit。

## 规则归属

每条规则只能有一个主要真源。判断顺序：

1. **套件入口判断**：`skills/cflow/SKILL.md`。只负责用户意图识别、入口推荐和最短流程推荐。
2. **专项生产能力**：对应专项 skill 的 `SKILL.md`。它必须包含该场景完整可执行的生产规则、失败闸门、结构模式和必要回归样例。
3. **作者表达偏好**：唯一 `profiles/voice-profile.md`，由 `$cflow-voice` 维护。
4. **普通生产资产**：`profiles/content-assets/`。只作为运行资产，不是通用规则真源。
5. **skill 治理流程**：`skills/cflow-maintain/SKILL.md`。
6. **吸收进化流程**：`skills/cflow-absorb/SKILL.md`。
7. **发现 metadata**：`agents/openai.yaml`。只维护展示名、简述和默认 prompt，不承载行为规则。

如果一条规则似乎适合多个 skill，先判断根行为：

- 入口判断规则放在 `$cflow`。
- 成稿、改稿、包装、短内容、营销、研究、SEO、案例、账号、声音等专项能力放在对应专项 skill。
- 作者长期表达偏好放在 voice profile。
- 具体案例、模板、结构资产和内容资产放在 `profiles/content-assets/`。
- 治理规则放在 `$cflow-maintain`。
- 吸收方法放在 `$cflow-absorb`。

需要在运行时稳定生效的规则必须进入实际会被调用的 `SKILL.md`。不能把规则放在不会被调用的位置，不能靠旧外部文件、通用说明、README 或 metadata 假装已经生效。

## 内置规则迁移

外部 reference、旧跨文件规则、旧 helper 和旧恢复逻辑都不能继续作为运行依赖。治理时按两层维护：

1. **入口 skill**：保留意图识别、入口推荐、最短流程和误路由防线。
2. **专项 skill**：保留自己场景内完整可执行的规则、质量闸门、结构模式和回归样例。

迁移判断：

- 仍有价值的规则，迁移到实际需要它的专项 skill。
- 迁移后 `SKILL.md` 是唯一运行入口，旧外部规则文件删除或保持已删除状态。
- 回归样例放在最容易失败的专项 skill，不放进跨文件说明。
- 如果某条规则连续在某个生产 skill 里失效，优先补该 skill 的本地闸门或回归样例，而不是继续强化入口或共享说明。
- 高风险质量门槛可以在专项 skill 本地重复，但重复必须服务运行稳定，不制造第二真源。

## 覆盖状态

审计规则时使用这些标签：

- **已覆盖**：当前唯一真源已经覆盖，不用改。
- **部分覆盖**：已有规则方向对，但需要收紧、扩展或移到更清晰位置。
- **重复**：多个位置表达同一规则，合并到最佳位置并删除重复。
- **冲突**：规则互相矛盾，选择符合 CFlow 边界和用户目标的版本；业务意图不清时问用户。
- **新规则**：当前没有覆盖，添加到最窄真源。
- **过时**：不再符合当前架构，删除。
- **应移动**：规则有价值，但放错文件。
- **应删除**：规则无效、误导、重复或属于旧架构。
- **应分流**：不进 skill 主规则，转给 profile、内容资产、发布环境笔记、review 经验、例子或测试用例。

## 反膨胀审计

反膨胀属于治理阶段，不是吸收阶段。它不能用来阻止 `$cflow-absorb` 提炼可迁移机制；只能在已经明确“要改哪里”后，检查修改是否造成无必要膨胀。

新增前依次检查：

1. 现有规则是否已经覆盖，只是执行时没遵守。
2. 是否能收紧一条已有规则，而不是新增平行规则。
3. 是否能合并相邻规则。
4. 是否应移动到另一个真源。
5. 是否有旧规则因为这次变更需要删除。
6. 是否只是例子、测试用例或生产资产，不应成为长期规则。
7. 是否属于作者画像、业务资产、发布环境短期经验或私有素材。

只有上面都不成立，才新增长期规则。新增规则必须说明它替代、合并或强化了什么；净新增必须说明收益大于维护成本。大改时追求净减少、净合并或净清晰。

## 语料型 skill 治理

维护含原始语料、作者风格、对标样本、案例库、训练数据、评估集、合成样本或生成脚本的 skill 时，先做资源分层。

资源可信顺序：

1. 原始语料。
2. 人工蒸馏。
3. 派生训练 / 评估样本。
4. 合成样本。
5. 生成脚本。
6. 测试输出。

治理规则：

- 原始语料与人工蒸馏、训练数据、合成样本或生成脚本冲突时，以原始语料为真源。
- 派生资源只能在证明不污染行为时保留。
- 如果旧训练集、合成样本、生成脚本或参考文件已经成为错误行为来源，应把它们视为旧架构的一部分处理。
- 重构完成后不要保留旧 helper、旧派生样本、旧模板或旧恢复路径。

## 重构规则

- 按根因收口，不按现象修补。
- 先确定单一来源和唯一真实边界，再迁移所有调用点。
- 迁移后不要保留旧 helper、旧流程、旧导出、兼容解释或旧恢复逻辑。
- 优先把原则规则移动到实际调用的 `SKILL.md`。
- 优先合并和替换，不叠加相邻规则。
- `SKILL.md` 是唯一规则入口；详细模式必须合并进主文件或删除，不能继续放在外部规则文件。
- 只有套件边界、编排规则或协作调度变化时才更新 `cflow`。
- 只有展示 metadata 过时时才更新 `agents/openai.yaml`。
- 删除、移动、重命名或改路由时，同时检查所有调用点，不留下旧引用。

## 发现入口同步

创建、删除或重命名 skill 后，必须同步 Codex 个人 skill 发现入口：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/sync_personal_skills.ps1 -PruneStale
```

同步脚本只创建缺失 junction，并且只删除 stale 的 CFlow junction：名字是 `cflow*`、类型是 junction、target 指向本仓库 `skills`、且 target 已不存在。

只修改现有 `SKILL.md` 内容、不创建 / 删除 / 重命名 skill 时，不运行同步脚本。

## 校验

默认运行：

```powershell
python scripts\quick_validate.py
```

需要额外校验的情况：

- 创建、删除或重命名 skill：先同步发现入口，再运行 quick validate。
- 改动套件路由、所有权边界或共享约定：校验全部 CFlow skills，并检查相关入口描述。
- 修改 `agents/openai.yaml`：检查 metadata 是否仍只承载展示信息。
- 删除旧文件：检查 `rg` 不再能搜到旧路径、旧 helper、旧导出或旧恢复逻辑。

## 提交

只有用户明确要求提交，或批准计划包含提交时，才在校验通过后提交。commit message 保持聚焦：

- `Update <skill> governance`
- `Move <rule> into <skill>`
- `Refine CFlow routing`
- `Remove duplicate <rule-area> guidance`
- `Add cflow-absorb`
