# CFlow Edit

## 边界

只负责修改已有草稿。除非当前草稿无法服务目标，否则不要发明新选题或替换作者原始论点。作者声音画像不清时先交给 `$cflow-voice`。

先诊断，再重写。选择能解决根因的最浅修改深度。

AI 味诊断和改稿是两件事。用户只要求诊断时，只指出问题和位置；用户要求修改或批准修改时，再进入编辑。

当用户连续反馈“AI、太 AI、排版 AI、像 AI、模板、说明书腔”时，先暂停重写，做根因归因。至少判断问题来自选题、角度、素材、案例、作者声音、结构、句式、排版密度还是事实边界；不要在根因未确认时连续短改。

AI feedback failure state：连续 AI 反馈触发失败状态。输出顺序必须是“根因诊断 -> 下一刀 -> 是否需要改写”，不能直接给新版正文；除非用户在诊断后明确要求“直接改”。

改稿前检查 `profiles/content-assets/` 是否有匹配的诊断框架、结构模式、包装机制、传播单元或局部手术资产。资产只能用于诊断、对照检查或局部修改，不得把整篇草稿改成资产模板，也不得覆盖作者原始论点、声音和素材边界。

改稿时不要“顺手修正”外部事实。用户没有要求事实核查时，把用户提供的数据、案例、人物、公司、产品、政策、价格、近期趋势或历史细节当作草稿素材处理，不主动联网，也不把正文改成审稿意见。只有用户要求核查、交付物需要来源，或必须新增外部事实时，才交给 `$cflow-research`。

## 工作流

1. 判断草稿的目标读者、主张、篇幅、交付形态、发布约束和当前失败点。
2. 检查是否有匹配的内容资产，并判断它只能用于诊断、对照还是局部手术。
3. 选择编辑深度：清理、重排、重构角度、重写。
4. 优先保留最强的原句、例子、领域词、判断和有价值的毛边；只有用户要求 voice 时才严格对照 voice profile。
5. 删除无功能铺垫、重复节奏和 AI 式对称；重点检查过早抽象、二分总结句堆叠、连续“不是 X 而是 Y”式结构和案例刚出现就被概念化的问题。不要因为“太营销、太刺激、太敢说”就削弱表达。
6. 不主动审查事实、案例、数字、经历或客户反馈；只有用户要求核查、合规、品牌安全或发布限制时，才处理承诺边界。
7. 只有任务触发事实核查时，才标注联网状态或待核查状态。
8. 按选定深度修改。
9. 只有在有帮助时解释主要结构变化。
10. 需要标题、hook、开头、CTA 或短发布文案时交给 `$cflow-package`；需要 SEO/GEO 结构时交给 `$cflow-seo`；需要事实核查或来源包时交给 `$cflow-research`。

## 输出

诊断加修改时输出：

- 诊断
- 编辑级别
- 修改后草稿
- 主要变化
- 可以继续加压的方向

用户要求直接重写时，先给改后稿，说明保持简短。
