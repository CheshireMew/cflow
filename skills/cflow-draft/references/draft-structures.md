# 成稿结构

## Brief 合同

```text
目标：
读者：
平台：
格式：
核心主张：
读者张力：
证据：
声音：
约束：
```

## 结构

### AIDA 销售稿

当草稿需要销售、转化或说服时使用。

```text
Attention
Interest
Desire
Objection handling
Proof
Action
```

先建立 desire，再引入产品、价格或 CTA。如果产品出现太早，读者会在还没承认问题前就感到被推销。

### 诊断型

```text
症状
错误诊断
根因
机制
应该怎么做
例子
收束句
```

### 实用指南型

```text
问题
常见建议为什么失败
原则
步骤
例子
陷阱
下一步动作
```

### 观点型

```text
主张
为什么重要
别人忽略了什么
推理
影响
反方观点
最终立场
```

### 故事到洞察型

```text
场景
张力
变化
洞察
经验
应用
结尾
```

### 故事销售型

当产品、社群、服务或 offer 需要通过故事定位时使用。

```text
客户或创作者场景
问题或压力
失败解决方案
转折点
guide、工具或机制
新结果
证据
行动
```

客户是 hero。品牌、产品或社群是 guide。除非格式明确是产品演示，不要让产品成为主角。

## 成稿机制

- 长可以，前提是一直有意思。先诊断哪里无聊，不要只因为长就删。
- 每句话都应该推进故事、澄清主张、增加欲望、处理异议，或把读者带到下一句。
- 用 “but / therefore” 逻辑推进故事。没有张力时，避免平铺直叙的 “and then”。
- 复杂主张要简单到第一次读就能懂。
- 尽量一句话只表达一个点。
- 销售或教育型草稿要把关键异议放进正文流动里，不要全部堆到结尾。

## 平台调整

- **短视频**：为口语节奏、短拍点、从场景到观点的移动写。
- **小红书/RED**：用可扫读结构、具体利益和生活细节。
- **LinkedIn**：用职业张力、决策逻辑和克制自信。
- **Twitter/X**：一条推进一个想法，保持顺序压力。
- **Newsletter/blog**：重视上下文、连续论证、例子和长期价值。

## 长文结构纪律

适用于 blog、newsletter、长文章和需要归档阅读的技术/商业长文。

- 如果 frontmatter 已经有 `title`，正文不要再重复一个 `# H1`。直接从开篇段落或 `##` 小节开始，避免渲染后出现两个大标题。
- 标题不要承担正文解释功能。避免把标题写成“主标：副标：再解释”的堆叠结构；标题只放核心概念，具体范围、背景和技术名词放到正文第一段自然引出。
- 小节标题用来帮助读者定位，不用编号制造机械感。除非用户明确要教程编号或文档目录，否则不要写“一、二、三”或“1. 2. 3.”式标题。
- 开篇要尽早点名主角、目标读者和这篇文章要解决的问题。不要用“本文将从多个维度深入探讨”这类空铺垫。
- 文章结尾自然收束。最后一节讲完就可以停，不需要强行加“总结”“最后”“结语”“写在最后”。
- 文末链接要克制。正文已经 inline 出现过的链接，不要在文末重复堆一遍；只有三条以上链接、或需要分组解释时，才使用“资源/链接合集”。

## 草稿质量检查

- 一个核心主张
- 目标读者清楚
- 有具体证据
- 没有无证据的确定性
- 外部事实、数据和真实案例已标注来源状态
- 未联网核查的信息没有被写成确定事实
- 没有泛泛鸡血
- 结尾说明发生了什么变化
- CTA 前已经建立 desire
- 异议已经通过证据、故事或直接承认处理
- 长文没有重复 H1、解释性标题堆叠或仪式化结尾
