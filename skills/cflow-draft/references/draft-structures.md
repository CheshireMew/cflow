# 成稿结构

## 共享合同

成稿受 `$cflow` 的 `references/content-production-contract.md` 约束。本文件只维护“第一版完整草稿”的题材结构和成稿应用，不重复维护通用写作纪律。

## Brief 合同

```text
目标：
读者：
篇幅：
交付形态：
发布约束：
核心主张：
读者张力：
可放大素材：
表达目标：
题材类型：
声音：
约束：
```

## 成稿职责

`cflow-draft` 只负责把稳定 brief、角度、大纲、转录、笔记或素材写成完整可发布一稿。它不做 CFlow 总编排。

上游可以来自 `$cflow`、`$cflow-angle`、`$cflow-marketing`、`$cflow-research`、`$cflow-case` 或用户直接提供的素材。无论从哪里进入，先把输入整理成成稿 brief，再开始写。

## 内容资产采用

成稿前检查 `profiles/content-assets/` 是否有匹配资产。优先匹配 frontmatter 中包含 `cflow-draft` 的资产，以及 `triggers` / `use_when` 与当前题材、结构或交付形态相符的资产。

可采用的资产类型：

- 长文结构模式
- 叙事推进方式
- 论证模板
- 案例用法
- 资源包装模板
- 读者张力展开方式
- 结尾行动路径

采用规则：

- 资产只提供结构、推进顺序、案例用法或表达机制。
- 不把资产中的人物、数字、案例、结果和权威背书写进当前草稿，除非用户素材已经提供。
- 如果资产适用条件不满足，只使用其中的抽象机制，或放弃采用。
- 需要短内容分发时，可以把资产交给 `$cflow-shortform` 做降维分发。

如果发现上游缺口：

- 主张弱：轻量修复；如果会改变内容方向，交给 `$cflow-angle`。
- offer / CTA / funnel 不清：交给 `$cflow-marketing`。
- hook / 标题 / 开头 / CTA 弱：交给 `$cflow-package`。
- 需要真实案例或故事设计：交给 `$cflow-case`。
- 需要搜索、来源、引用或最新事实：交给 `$cflow-research`。
- 作者声音是强约束：交给 `$cflow-voice`。

不要因为用户从 `$cflow-draft` 开始，就把所有上游和下游问题都塞进 draft 内硬做。

## 结构

### AIDA 销售稿

当草稿需要销售、转化或说服时使用。

```text
Attention
Interest
Desire
Objection handling
Proof
Action
```

先建立 desire，再引入产品、价格或 CTA。如果产品出现太早，读者会在还没承认问题前就感到被推销。

销售稿允许强 urgency、强利益、强对比和强 CTA。夸张本身不是错误，很多时候是转化杠杆。默认不做可信度审查、不加免责声明、不主动降级表达；只有用户要求严谨、合规、发布限制或品牌安全时，才检查不可兑现承诺、过度浮夸和证据无法承载的确定性。

渠道情报型、机会窗口型、限时入口型文案按 `$cflow-marketing` 的入口型转化规则处理，不套 AIDA 的默认顺序。

### 渠道情报型转化稿

当 `$cflow-marketing` 已判断当前任务是渠道情报、机会窗口或入口型转化时使用。

```text
截止时间 / 窗口变化
入口对象
稀缺性
内行信息差
利益点列表
强对比
福利补强
操作 CTA
```

写法纪律：保留短句、列表、符号、消息感、紧迫感和直接 CTA；不要写成完整产品介绍。具体主入口、稀缺性、风险提醒和多链接排序以 `$cflow-marketing` 为准。

### 诊断型

```text
症状
错误诊断
根因
机制
应该怎么做
例子
收束句
```

### 实用指南型

```text
问题
常见建议为什么失败
原则
步骤
例子
陷阱
下一步动作
```

### 创作者教程 / 工具上手稿

当用户要写教程文章、工具上手、使用体验或面向粉丝的实用指南时，先判断交付物是“内容文章”还是“产品手册”。除非用户明确要求手册、文档、速查表或 FAQ，否则默认写成创作者文章。

```text
为什么现在值得关心
读者的具体处境
一个真实使用场景
核心操作或关键机制
作者判断和取舍
容易踩的坑
下一步可以怎么试
```

写法纪律：

- 不把资料平铺成完整功能清单。先选最能服务读者行动和阅读理由的信息。
- 命令表、快捷键、FAQ、参数说明和长清单默认后置、压缩或作为附录；只有用户明确要手册时才放进正文主结构。
- 教程也要有作者判断：什么最值得先试、什么新手容易误解、什么场景真的有用、什么不必一开始学。
- 先写具体使用场景，再解释功能。不要从“它支持什么”开始一路介绍到结尾。
- 口语化不是本人味。不要把说明书腔简单改成过度随便的聊天腔；声音不清时用自然、直接、有判断的中文。

### 观点型

```text
主张
为什么重要
别人忽略了什么
推理
影响
反方观点
最终立场
```

### 故事到洞察型

```text
场景
张力
变化
洞察
经验
应用
结尾
```

### 源头资产型长文

当用户想建立内容飞轮、知识资产、个人品牌主线，或后续要拆成短内容、短脚本或短发布文案时使用。

```text
读者正在付出的代价
本篇核心主张
一个具体场景或亲历问题
机制解释
可执行路径
异议或失败做法
可复用判断
下一步行动或后续拆分方向
```

写法纪律：

- 长文要先作为完整资产成立，而不是为了拆短而写成素材仓库。
- 每个小节最好能独立承载一个判断、场景、清单、案例或反常识，方便后续交给 `$cflow-shortform` 拆分。
- 源头资产必须有作者判断。不要把资料整理成百科、报告或趋势汇总。
- 如果只是记录灵感，先收束成一个核心主张；如果主张不稳，交给 `$cflow-angle`。
- 如果后续要分发，结尾给出可拆分单元，而不是直接在长文里塞满多个短文案。

### 故事销售型

当产品、社群、服务或 offer 需要通过故事定位时使用。

```text
客户或创作者场景
问题或压力
失败解决方案
转折点
guide、工具或机制
新结果
说服动作
行动
```

客户是 hero。品牌、产品或社群是 guide。除非格式明确是产品演示，不要让产品成为主角。

## 成稿机制

- 先按共享合同确认主任务、主张、读者和素材边界，再选择题材结构。
- 长可以，前提是每一段都服务主任务。不要只因为长就删，先诊断哪里失去推进功能。
- 用 “but / therefore” 逻辑推进故事。没有张力时，避免平铺直叙的 “and then”。
- 销售或教育型草稿要把关键异议放进正文流动里，不要全部堆到结尾。

## 引流资产插入

成稿时如果内容自然适合承接用户提供的个人资产或 profile，可以调用 `$cflow-marketing` 选择一个主引流动作。

使用规则：

- 单篇默认只插一个主入口，不把所有链接堆到文末。
- 具体资产清单、链接、邀请码和私有入口来自用户 profile 或资产档案，不写进通用成稿规则。
- 用户明确给出的发布约束不方便放链接时，写成用户可执行的低摩擦入口。
- 如果引流会破坏正文节奏，只在交付后给一句提醒，不强行写入正文。
- 用户明确要求纯内容、不加 CTA 时，不主动插入。

## 呼吸感

呼吸感的通用定义见共享合同。成稿时重点处理长内容的段落密度和结构起伏。

- 不要连续十句都满格输出。强判断、强利益或强情绪之后，接一个具体例子、短落点或行动句。
- 段落不要承担太多功能。一个段落通常只做一件事：抛判断、讲场景、解释机制、列利益点、处理异议或推动 CTA。
- 长句负责推进复杂关系，短句负责打断和落点。不要全短句，也不要全解释句。
- 列表用于扫读和连续暴击，段落用于解释和转折。两者要交替，不要把所有信息揉成一团。
- 渠道情报和硬广可以高压，但高压之后要有清楚的操作落点。
- 长文每一小节都要有起伏：进入、推进、停顿、转向或收束。

## 长文结构纪律

适用于长文章和需要归档阅读的技术/商业长文。

- 如果 frontmatter 已经有 `title`，正文不要再重复一个 `# H1`。直接从开篇段落或 `##` 小节开始，避免渲染后出现两个大标题。
- 标题不要承担正文解释功能。避免把标题写成“主标：副标：再解释”的堆叠结构；标题只放核心概念，具体范围、背景和技术名词放到正文第一段自然引出。
- 小节标题用来帮助读者定位，不用编号制造机械感。除非用户明确要教程编号或文档目录，否则不要写“一、二、三”或“1. 2. 3.”式标题。
- 开篇要尽早点名主角、目标读者和这篇文章要解决的问题。不要用“本文将从多个维度深入探讨”这类空铺垫。
- 文章结尾自然收束。最后一节讲完就可以停，不需要强行加“总结”“最后”“结语”“写在最后”。
- 文末链接默认服务行动路径。只有用户要求长文阅读体验或归档整洁时，才克制重复链接。

## 草稿质量检查

- 一个核心主张
- 目标读者清楚
- 表达强度足够
- 有呼吸感，强句、解释、列表和停顿不是同一密度
- 具体素材被充分放大
- 题材结构服务主任务，而不是把资料平铺成说明文
- 只有用户要求严谨核查时，才检查来源、事实状态和承诺边界
- 没有把用户未要求核查的素材强行改成风控说明或保守提示
- 没有无功能废话
- 结尾说明发生了什么变化
- CTA 前已经建立 desire
- 异议只在影响转化时处理
- 长文没有重复 H1、解释性标题堆叠或仪式化结尾
