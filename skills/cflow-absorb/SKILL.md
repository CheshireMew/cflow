# CFlow Absorb

## 边界

`cflow-absorb` 负责让 CFlow 从好信息里进化。它的主目标不是治理知识库，而是发现输入里真正能提高内容生产质量、判断质量和执行质量的机制，并把这些机制升级到正确的生产 skill。

适用输入：

- 外部写作方法论、课程笔记、白皮书、操作手册。
- 优质内容、爆款拆解、对标账号、样稿和修改前后对比。
- 用户对 CFlow 输出的失败反馈、连续纠偏和使用失败现场。
- 整段 CFlow 对话流程中的误读、错路由、边界混淆、连续纠偏失效和 skill 协作断点。
- 用户亲自修改过的标题、hook、opening、CTA、正文或发布文案。
- 新的工作流、生产原则、内容审美判断或执行标准。

不负责：

- 规则库去重、旧架构删除、兼容层清理、发现入口同步。这些交给 `$cflow-maintain`。
- 普通成稿、改稿、标题、营销、研究和内容表现复盘执行。这些交给对应生产 skill。
- 把作者个人口癖、私有身份、固定格式或单篇素材直接写成通用规则。

`cflow-absorb` 可以审计 CFlow 使用失败现场，但审计对象是“系统执行为什么断”，不是“某条内容为什么表现好或不好”。内容本体、发布表现、评论和数据复盘归 `$cflow-review`；对话流程、skill 调用、用户意图识别、纠偏回收和规则执行断点归 `cflow-absorb`。

## 核心原则

面对新材料，先吸收，再治理。

默认问题不是“能不能拒绝沉淀”，而是：

```text
它让哪类内容、哪类判断、哪类生产动作变强？
它改善读者行为链的哪一环？
它用了什么表达动作改变读者进入、理解、相信、记住或传播的方式？
它应该升级哪个生产 skill 的默认能力？
它哪些部分只是作者个人风格、单篇素材或不可复制条件？
```

可迁移内容机制默认优先进入对应生产 skill 的 `SKILL.md` 或 `references/`。只有局部可复用、证据弱、过度套用风险高，或不适合约束默认行为时，才进入 `profiles/content-assets/`。

## 工作流

1. **拆分输入**：把长材料拆成独立信息单元，至少区分内容机制、表达机制、读者行为机制、写作技巧、结构机制、包装机制、案例机制、声音偏好、平台观察、事实资料、测试样本、对话执行断点和治理请求。
2. **三层扫描**：分别检查它选择了什么信息和角度、用了什么表达动作、触发了什么读者行为；不要只吸收“说了什么”，也要吸收“怎么让读者读下去、信下去、记住或传播”。
3. **识别内容价值**：逐项判断它改善停下来、继续读、理解、相信、记住、行动还是复访。
4. **提炼机制**：把审美词、作者经验和例子翻译成具体生产动作；表达形态、首句、断行、顺序、密度、收束、标点和高频短语都要先判断是否承担功能，再决定是通用机制、voice 偏好还是拒绝项。
5. **解释力校验**：如果输入包含多个样本或高表现样本，吸收计划必须能解释代表样本或 top 样本为什么有效；解释不了时，回到内容机制、表达机制和读者行为机制重新扫描。
6. **判断迁移性**：区分可迁移机制、专项规则候选、生产资产候选、测试用例、作者画像候选、发布环境笔记和拒绝项。
7. **确定生产归属**：优先找最窄生产 skill，例如 `cflow-draft`、`cflow-package`、`cflow-check`、`cflow-shortform`、`cflow-angle`、`cflow-case`、`cflow-viral`。
8. **判断升级层级**：默认能力进 skill/reference；局部模式进 `profiles/content-assets/`；个人表达偏好交给 `$cflow-voice`；事实缺口交给 `$cflow-research`。
9. **生成吸收计划**：说明要升级哪些生产能力、拒绝哪些不可迁移部分、是否需要治理审计，并说明是否通过解释力校验。计划必须先用普通话说明“以后 CFlow 会多做什么、少做什么”，再列文件和归属；必要时给 before / after 示例。
10. **请求批准**：在用户明确批准前，不修改任何 CFlow skill 文件。
11. **应用变更**：只修改批准范围。涉及去重、移动、删除、旧架构清理时，调用 `$cflow-maintain` 的治理协议。
12. **纠偏回收**：如果用户指出“没看懂、不是这个、太 AI、太长、漏了某个结构、你理解错了、你判断也有问题”，必须把它当成 absorb 失败反馈，先命名根行为，再判断是 absorb 协议缺口、生产 skill 缺口、路由缺口、边界混淆还是执行失误。
13. **校验**：运行 `python scripts\quick_validate.py`；如果创建、删除或重命名 skill，再运行 sync 脚本。

## 内容效果链

| 环节 | 判断问题 |
|---|---|
| 停下来 | 它是否让读者第一眼知道为什么现在要看？ |
| 继续读 | 它是否制造真实悬念、冲突、利益或推进感？ |
| 理解 | 它是否让抽象问题变具体，或让复杂信息更容易消化？ |
| 相信 | 它是否增加证据、案例、代价、边界或作者判断的可信度？ |
| 记住 | 它是否产生可复述的句子、场景、动作、结构或视觉信号？ |
| 行动 | 它是否让收藏、转发、评论、私信、购买、预约或下一步动作更自然？ |
| 复访 | 它是否沉淀为栏目、作者识别、方法资产、信任资产或后续选题入口？ |

说不清改善哪一环的信息，不能升级为默认生产规则；但仍要判断是否能作为测试用例、例子、资产或 voice 候选证据。

## 归属矩阵

| 信息单元 | 优先归属 |
|---|---|
| 对话流程误读、skill 名称被当成内容对象、连续纠偏没触发重判 | `$cflow-absorb` |
| 选题来源、读者痛点、栏目入口 | `$cflow-topic` |
| 主张、矛盾、读者张力、premise | `$cflow-angle` |
| 长文结构、题材结构、完整草稿推进 | `$cflow-draft` |
| 标题、hook、opening、CTA、短发布文案 | `$cflow-package` |
| 短内容结构、短脚本、短链路推进 | `$cflow-shortform` |
| 发布前判断、能不能发、哪里会失败 | `$cflow-check` |
| 案例、故事、类比、证明动作 | `$cflow-case` |
| offer、funnel、转化桥、行动路径 | `$cflow-marketing` |
| 分享动机、截图点、传播单元 | `$cflow-viral` |
| 搜索意图、AI 可引用结构 | `$cflow-seo` |

| 发布后指标、评论和反馈学习 | `$cflow-review` |

| 去重、冲突、旧架构、唯一事实源 | `$cflow-maintain` |

## 作者画像分流

如果输入里出现以下信号，必须先分桶，不得直接写入通用 skill：

- “我讨厌 / 我喜欢 / 以后别 / 以后都 / 记住这个”
- “这不像我 / 这才是我的写法 / 正确但不像本人”
- “我改了一下 / 我稍微修改了 / 这样写才对 / 参考我这个版本”
- 用户亲自修改标题、hook、opening、CTA 或短发布文案
- 对固定词、句式、排版密度、语气、文章入口方式的个人偏好

分桶：

```text
通用机制：
生产 skill 升级：
作者画像：
单篇 brief：
生产资产候选：
测试用例：
拒绝沉淀：
```

只有跨用户、跨题材成立，并且能明确改善内容效果链的机制，才升级到通用生产 skill。
