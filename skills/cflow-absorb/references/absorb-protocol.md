# 吸收进化协议

## 输入分类

长材料先拆分，不要整包归类。

常见信息单元：

- 写作技巧：结构、节奏、论证、案例、开头、标题、hook、CTA。
- 内容机制：提升停留、继续读、理解、相信、记住、行动或复访的生产规律。
- 表达机制：首句、第一段、断行、顺序、密度、定调、转折、收束、标点、重复句式和高频短语如何改变读者读法。
- 读者行为机制：内容如何触发停留、评论、收藏、转发、截图、复述、私信、购买、复访或二创。
- 样稿证据：用户原文、优秀样稿、修改前后对比、失败输出。
- 作者偏好：口癖、表达禁区、价值判断、节奏、排版密度。
- 对标模式：外部账号、爆款、栏目、发布节奏、包装方式。
- 发布环境观察：平台、媒介、字数、链接、审核、比例、算法或短期表现。
- 事实资料：数据、来源、事件、人物、产品功能、政策或当前信息。
- 测试用例：能验证规则是否执行的输入、输出或失败现场。
- 对话执行断点：整段 CFlow 对话中的误读、错路由、边界混淆、skill 协作失败、连续纠偏失效或规则已存在但未执行。
- 治理请求：去重、移动、删除、重命名、同步、校验和唯一事实源。

每个信息单元都要回答：

```text
信息类型：
内容效果：
可迁移机制：
不可迁移条件：
主要归属：
升级层级：
处理动作：
```

## 三层机制扫描

吸收样本时必须同时扫描三层，不要只提炼内容层。

### 1. 内容机制

检查它选择了什么信息、角度、案例、证据、判断和读者任务。

问题：

```text
它说了什么？
它没有说什么？
它把哪类信息前置、后置、压缩或删除？
它靠事实、案例、数字、冲突、主张还是作者判断成立？
```

### 2. 表达机制

检查它如何通过表达动作改变读者读法。

问题：

```text
首句承担什么功能：定调、制造悬念、给结果、给身份、给场景、给冲突，还是筛选读者？
第一段是否完成进入理由，还是只补背景？
断行、段落密度、短句、转折和标点是否服务推进，而不是形式习惯？
结尾如何收束：判断、问题、行动、反讽、警示、记忆句，还是开放讨论？
高频短语是作者口癖、平台习惯，还是承担定调、分类、转折、情绪、可信度或传播姿态？
```

### 3. 读者行为机制

检查它让读者更可能做什么。

问题：

```text
它让读者为什么停下来？
哪一句让读者继续读？
哪个细节让读者相信或收藏？
哪一句、哪一屏或哪种态度能被截图、转发、复述或评论？
读者分享时是在替自己表达什么身份、情绪、立场、提醒或信息差？
```

只有能说清至少一层机制的信息，才进入后续迁移判断。只像风格、但说不清读者行为效果的内容，先标为 voice 候选或拒绝沉淀。

## 解释力校验

面对多个样本、对标账号、爆款列表或带指标内容库时，吸收计划必须解释代表样本为什么有效。

默认做法：

```text
1. 选 top 样本、异常样本和代表样本。
2. 用当前提炼出的机制逐条解释：它为什么停住读者、为什么继续读、为什么收藏/评论/转发。
3. 如果某个高频表达动作解释不了，回到三层机制扫描，不要直接归为风格或忽略。
4. 如果 top 样本有效原因依赖作者身份、私有信源、题材红利、热点时机或平台分发，标为不可复制条件。
5. 如果多个样本共享同一表达动作，并且能解释读者行为，优先作为生产规则候选、测试用例或资产候选。
```

输出吸收计划时必须说明：

```text
代表样本：
当前机制能解释什么：
解释不了的现象：
需要回扫的层级：内容机制 / 表达机制 / 读者行为机制
不可复制条件：
```

## 最大化吸收

面对外部方法论、优质内容、课程笔记、长素材、对标拆解或失败反馈，先尽可能抽取有用部分，再做边界分流。

必须形成学习清单：

```text
可迁移机制：
专项规则候选：
表达机制候选：
生产资产候选：
测试用例：
例子：
作者画像候选：
发布环境笔记：
拒绝项：
```

判断规则：

- 不适合进通用规则，不等于没有价值。
- 已覆盖，不等于无需沉淀；如果输入提供更好的执行模板、失败样本或判断问题，可以收紧对应生产 skill。
- 外部方法论不能整包照收，但要拆到可迁移机制、不可复制条件、使用边界和下一次调用方式。
- 表达动作不能因为短、小、像风格就跳过；先判断它是否改变读者进入、理解、信任、记忆或传播。
- 只出现一次但机制清楚时，优先作为候选测试、例子或资产；如果它解释了高频失败行为，可以升级成生产规则。
- 只有说不清效果链、也不能作为资产、例子、测试或证据的信息，才拒绝沉淀。

## 吸收计划可读性

吸收计划不是只给维护者看的文件清单。用户批准前，必须先说明行为变化。

计划开头必须回答：

```text
这次要让 CFlow 多做什么？
这次要让 CFlow 少做什么或禁止什么？
用户下次给类似材料时，输出会和现在有什么差别？
有没有一个 before / after 能证明差别？
```

不要只写：

```text
Production skill upgrades:
Files to change:
Validation plan:
```

必须先写成用户能判断的动作：

```text
以后处理长英文科技消息时，先压成 4 到 5 段短链路，不按素材字数等比例展开；结尾停在数字差或后果上，不补“这不是 X，而是 Y”的抽象尾巴。
```

如果用户回复“没看懂”或追问“你到底想增加什么”，说明计划可读性失败。先重写行为变化说明，再继续请求批准。

## 纠偏回收

用户指出输出失败时，不只修当次文本，还要判断是否暴露了吸收或生产规则缺口。

常见纠偏信号：

- “没看懂”：吸收计划没有说明行为变化。
- “你漏了 X”：三层机制扫描或解释力校验不足。
- “太长”：生产 skill 没有按信息密度压缩。
- “AI 味”：可能是补尾巴、二分总结、抽象升华、素材等比例展开或 voice 失真。
- “我期望的是这样”：用户提供了目标结构，应作为样式约束和测试用例候选。

处理步骤：

```text
1. 命名根行为，不只道歉或重写。
2. 判断归属：absorb 协议缺口 / 生产 skill 缺口 / 共享合同未执行 / 单次执行失误。
3. 如果是高频或高风险缺口，补进对应 skill 的硬检查。
4. 如果用户给出目标结构，抽象为通用结构，不把单例照搬成规则。
5. 产出修正版时，先满足用户结构，再说明已修的规则。
```

## 默认升级顺序

当输入是内容方法论或样稿时，默认按下面顺序判断：

1. 是否应该成为某个生产 skill 的默认能力。
2. 是否应该进入该 skill 的 reference，作为结构、流程、判断问题或质检项。
3. 是否应该进入 `cflow-check`，作为发布前失败判断。
4. 是否应该进入 `profiles/content-assets/`，作为局部可调用资产。
5. 是否应该成为测试用例或例子。
6. 是否应该交给 `cflow-voice` 作为作者画像或候选证据。
7. 是否应该拒绝沉淀。

不要把 `profiles/content-assets/` 当成优质方法论的默认归宿。资产层只适合局部模式、弱证据模式、高过度套用风险模式或不应改变默认行为的模式。

## 品味翻译

不要把“高级、有质感、抓人、松弛、颗粒感、人味”等词直接写成规则。

必须翻译成具体动作：

- 换入口。
- 删解释。
- 补场景。
- 保留代价。
- 强化判断。
- 调整段落密度。
- 改变首句功能。
- 改变信息顺序。
- 改变收束方式。
- 增加定调、转折或态度句。
- 增加记忆句。
- 改变视觉层级。
- 增加过程、阻碍、动作或证据。

如果建议只会让输出更完整、更顺滑、更像方法论，但不能提升停留、理解、相信、记忆、行动或复访，标记为伪规则。

## 失败反馈吸收

处理失败反馈时，先命名根行为：

- 用户意图识别错误。
- skill 名称被当成内容对象，而不是执行协议。
- 执行 skill、内容对象和交付形态没有分清。
- 写作机制未识别。
- 规则缺失。
- 规则已存在但没有执行。
- 规则放错位置。
- 默认资产未被调用。
- 生产 skill 缺默认能力。
- 路由缺失。
- 边界冲突。
- 连续纠偏没有触发任务重判。
- 作者画像冲突。
- 测试用例不足。

如果失败来自“生产时不会读取资产”，优先判断是否应把资产机制升级到生产 skill 的默认规则，而不是继续补资产。

## 对话流程断点审计

当输入是一整段 CFlow 使用失败现场或连续纠偏对话时，`cflow-absorb` 要审计的是执行链路，不是复盘某条内容本身。

先按时间线标出：

```text
用户原始任务：
用户点名的 skill：
真实推广对象或内容对象：
期望交付形态：
第一次误读发生在哪里：
第一次纠偏说了什么：
系统是否重判任务对象、执行协议和交付形态：
后续是否继续沿用错误策略：
最终用户认可的版本或判断：
```

再定位断点类型：

- **对象错置**：把用户点名的 skill、工具、文件或协议当成正文要推广的对象。
- **协议失效**：用户点名某个 skill，是要求按它的工作流执行，但系统没有执行其质量门槛。
- **默认能力缺失**：某个生产 skill 没有完成主交付物所需的基础能力。
- **过度路由**：遇到“平淡、不吸引人、没点击欲”等反馈时，直接切到 package/viral，而不是先判断当前生产 skill 是否本来负责这个质量。
- **纠偏未重判**：用户已经指出“不是这个”，系统仍然在旧理解上改句子。
- **规则已存在未执行**：规则真源已有要求，但输出没有按规则处理。

对话流程断点输出必须包含：

```text
根断点：
不是哪类问题：
暴露的缺失规则：
应该升级的 skill：
是否需要修改 cflow 路由：
是否需要修改生产 skill 默认质量门槛：
可作为测试用例的用户原话：
```

如果断点来自某个生产 skill 的默认能力不足，优先修改该生产 skill；不要要求用户下次手动追加另一个 skill 来补救。

## 泛化检查

从样稿或失败案例提炼机制时，禁止把具体发布环境、交付形态、对象、行业或文案场景直接固化为触发条件。

先做同类替换测试：

```text
把案例中的平台、题材、对象、行业或素材换成同类变量后，这个机制是否仍然改善内容效果链？
```

如果仍成立，写成可迁移生产规则；原案例只作为例子或测试用例。

## 治理交接

当吸收计划涉及以下动作时，交给 `$cflow-maintain` 做治理审计：

- 删除旧规则。
- 移动规则真源。
- 合并重复规则。
- 处理边界冲突。
- 创建、删除或重命名 skill。
- 清理旧 helper、旧导出、旧恢复逻辑。
- 同步个人 skill 发现入口。

吸收计划必须说明：

```text
治理动作：
为什么需要治理：
要保留的唯一事实源：
要删除的旧事实源：
```

## 校验

吸收修改后运行：

```powershell
python scripts\quick_validate.py
```

如果创建、删除或重命名 skill，再运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\sync_personal_skills.ps1 -PruneStale
python scripts\quick_validate.py
```
