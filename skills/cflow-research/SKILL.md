# CFlow Research

## 边界

`cflow-research` 负责搜寻资料、核查事实、评估来源、整理证据、标注不确定性，并把研究结果交接给内容生产、营销、SEO、案例或复盘 skill。

它必须自己完成研究任务里的核心判断：是否联网、来源等级、时间敏感性、说法是否成立、证据是否可用、材料能支持什么、不能支持什么、哪些是事实、哪些是观点、哪些只是推测、哪些需要继续核查。不能把这些判断外包给 `$cflow-draft`、`$cflow-edit`、`$cflow-check`、`$cflow-marketing` 或任何“合同”。

研究结果必须服务内容任务。不要为了“资料更全”无限扩展。先明确要支持哪个主张、选题、案例、竞品判断、SEO brief、营销判断、事实边界或发布风险。

不负责：

- 写完整正文、改稿、包装标题、生成营销文案或制作视觉 brief；这些交给对应生产 skill。
- 替内容决定最终主张、角度、CTA、结构或发布判断；research 只提供证据、边界和安全写法。
- 把未核查材料写成事实，或用模糊归因、猜测补洞替代来源。
- 用户只是要求成稿、改稿、包装或营销文案时，不因为素材里出现产品、价格、活动、政策、时间节点或公司信息就自动联网。只有研究任务被触发，或事实会改变交付物安全性时，才进入研究。

触发研究后，如果需要实时信息、外部事实、数据、人物、公司、产品、政策、价格、趋势、历史事件、竞品现状或来源引用，优先使用当前环境可用的联网工具。没有联网能力时，明确标注“未联网验证”，并请求用户提供来源或允许基于已有材料做离线研究。

## 入口判断

进入 `cflow-research` 后先判断研究任务类型：

- **事实核查**：判断一个说法是否支持、部分支持、不支持或无法确认。
- **背景研究**：快速理解话题、人物、公司、产品、事件、政策或历史。
- **案例搜寻**：寻找能支撑主张的真实案例、历史事件、用户样本或反面案例。
- **数据搜寻**：寻找统计数据、指标、报告、口径、趋势和可引用数字。
- **来源包 / 引用包**：为内容准备 source pack、引用材料和证据摘要。
- **反方证据**：寻找反例、限制、争议、失败案例和不可复制条件。
- **趋势扫描**：查看近期变化、信号、时间线和不确定性。
- **竞品资料**：收集竞品页面、广告、价格、评论、用户反馈和公开材料。
- **读者兴趣材料**：寻找真实使用场景、社区讨论、用户问题、实践文章和读者语言。
- **局部补证据**：上游已有主张、结构、角度或草稿时，只补当前证据缺口。

## 工作流

1. **定义研究任务**：事实核查、背景研究、案例搜寻、数据搜寻、来源包、引用包、竞品资料、趋势扫描、读者兴趣材料、外部使用案例或反方证据。
2. **确定研究问题**：把模糊请求改写成 1 到 3 个可搜索、可验证的问题。
3. **确认用途**：研究要服务哪个内容任务、主张、段落、营销判断、SEO brief、案例设计或发布风险。
4. **选择来源层级**：事实核查优先官方/一手资料；普通内容参考优先真实案例、社区使用场景、用户问题、实践文章和能支撑读者张力的材料，再用一手资料校验定义和边界。
5. **执行搜索和核查**：使用联网工具或用户提供材料；关键事实尽量交叉验证，不只看搜索摘要。
6. **分层记录**：区分已确认事实、来源观点、真实使用场景、读者痛点、合理推测、争议点、未核查项和不可用材料。
7. **整理证据包**：只保留能服务内容任务的资料，标注来源、时间、可信度、限制和用途。资料如果只能证明“技术上存在”，但不能帮助文章更好读、更可信或更想收藏，应压缩为背景校验。
8. **给安全写法**：对敏感、时间变化、单一来源、争议或不确定材料，给出可安全写法。
9. **交接给生产 skill**：交接时说明每个来源能支持什么、不能支持什么，而不是只给链接。

## 来源标注

研究输出必须标注：

```text
联网状态：已联网核查 / 用户提供来源 / 未联网验证
来源等级：一手 / 专业资料 / 权威二手 / 普通二手 / 社媒信号 / 未知
时间敏感性：高 / 中 / 低
来源数量：
仍需核查：
```

不要把未核查信息写成事实。查不到就说查不到。

## 来源优先级

优先级从高到低：

1. **官方/一手资料**：政府、公司官网、原始公告、公开财报、原始论文、原始数据、当事人公开声明。
2. **专业资料**：学术论文、行业报告、数据库、标准文件、专业机构。
3. **权威媒体**：有编辑流程和事实核查能力的媒体。
4. **普通二手资料**：博客、百科、行业文章、播客整理。
5. **受众信号**：评论、帖子、论坛、影音内容、用户反馈。
6. **未知来源**：无法确认出处的截图、转述、搬运内容。

不同任务允许不同来源：

- 写历史事实、政策、价格、产品、人物和公司信息时，优先一手或权威来源。
- 研究情绪、舆论、用户语言、读者痛点和社区用法时，社媒信号可以有价值，但不能当事实结论。
- 普通介绍文章、观点文章、工具发现、工作流复盘和创作者内容，优先寻找能帮助读者进入的材料：真实使用场景、外部案例、社区讨论、相似工作流、读者痛点、反方经验和可复述故事。技术文档只用于校验关键事实，不得抢走文章主线。
- 竞品资料可以收集广告、评论、价格页、落地页和用户反馈；要拆内容机制时交给 `$cflow-review`。

## 交叉验证

关键事实尽量满足：

- 至少两个独立来源互相支持。
- 时间敏感信息检查发布日期、更新日期和当前状态。
- 数据要看口径、样本、地区、时间范围。
- 历史事件要避免单因果简化。
- 公司、产品、价格、政策以官方或近期来源为准。
- 案例要记录真实性和可迁移边界。

如果只能找到单一来源，要标注：

```text
来源数量：单一来源
风险：需要进一步确认
安全写法：
```

如果来源之间冲突，要标注：

```text
冲突点：
各来源说法：
更可信来源：
不能确认的部分：
安全写法：
```

## 事实分层

研究记录不要混写。按层级整理：

- **已确认事实**：来源可靠，能直接使用。
- **来源观点**：某个作者、媒体、报告的判断，不等于事实。
- **真实使用场景**：用户、社区、案例或评论里出现的真实使用信号。
- **读者痛点**：可用于内容张力或营销判断的用户语言和困境。
- **合理推测**：基于材料的推断，需要标注。
- **争议点**：来源之间不一致或解释不同。
- **未核查项**：还没找到可靠来源。
- **不可用材料**：来源弱、过时、断章取义、与任务无关或只能制造噪音。

## 局部补证据

当上游已经有主张、结构、角度或草稿时，研究只补当前缺口：数据、真实案例、反方证据、来源、定义边界、读者信号或竞品材料。不要因为开始搜索就重启选题、改写全文、扩展成资料百科或替下游 skill 重新设计结构。

局部补证据前先标注：

```text
要支持的主张：
当前结构：
证据缺口：
不需要研究的部分：
交接对象：
```

搜索结果只保留能让内容更可信、更具体、更好读或更可行动的材料。只能证明“资料存在”但不服务内容任务的材料，压缩为背景校验或拒绝使用。

## 搜索纪律

- 先明确研究问题，再搜索。
- 搜索词要覆盖同义词、英文/中文、官方名称、时间范围。
- 优先打开原始来源，不只看搜索摘要。
- 对近期信息，检查发布日期和更新日期。
- 对数据，记录口径，不只摘数字。
- 对案例，记录真实性和可迁移边界。
- 对争议议题，主动找反方或限制条件。
- 对专业主题，优先查原始论文、标准、官方文档或权威机构。
- 对产品和公司信息，优先查官网、公告、文档、财报、公开声明和近期权威报道。
- 对社媒、论坛、评论和用户反馈，只把它们作为受众信号、使用场景或舆论材料，不直接写成事实结论。
- 查不到时停止编造，输出“无法确认”。

## 研究输出反 AI 味检查

`cflow-research` 不负责写作 skill 的反 AI 味，但必须防止研究输出变成 AI 式资料堆砌或伪事实。

重点检查：

- 是否把搜索摘要当成来源。
- 是否把未核查信息写成事实。
- 是否用“资料显示、专家认为、行业观察者认为”等模糊归因替代具体来源。
- 是否为了完整感堆很多与任务无关的背景。
- 是否把来源观点写成已确认事实。
- 是否用合理想象补洞。
- 是否把社媒信号当成统计结论。
- 是否只给链接，没有说明来源能支持什么。
- 是否忽略时间敏感性和发布日期。
- 是否为了证明主张只找支持证据，没有找限制或反方。

命中时先删、分层、降级或标注未确认。研究交付物的目标是让下游知道“能写什么、不能写什么、怎么安全写”，不是显得资料很多。

## 常见错误

- 未联网却写得像已经核查。
- 查不到仍然编一个合理答案。
- 用搜索摘要替代原始来源。
- 只列链接，不说用途和限制。
- 把二手文章里的判断当成事实。
- 把旧数据、旧价格、旧政策当成当前状态。
- 不记录数据口径、地区、样本和时间范围。
- 为了资料全面，把文章任务扩成百科。
- 技术文档抢走普通内容主线。
- 用社媒评论证明事实结论。
- 只找支持主张的证据，不找反例和限制。
- 不标注单一来源风险。
- 把“不可用材料”混进可用证据。
- 把研究结论直接写成正文，不交代事实边界。

## 路由

只在问题不属于 `cflow-research` 时路由：

- **可写成故事的案例、历史事件、类比或反面样本**：交给 `$cflow-case`。
- **证据包已经完成，需要写成长文、教程、脚本或销售稿**：交给 `$cflow-draft`。
- **已有草稿需要把证据嵌入、改结构或降 AI 味**：交给 `$cflow-edit`。
- **搜索意图、关键词、SERP 结构、FAQ 或 AI answer 结构**：交给 `$cflow-seo`。
- **转化证明、客户证据、市场资料、竞品 offer 或 CTA 用法**：交给 `$cflow-marketing`。
- **已提供样本，需要拆内容机制或发布表现**：交给 `$cflow-review`。
- **发布后数据、评论、转发、截图、私信反馈和表现复盘**：交给 `$cflow-review`。
- **标题、hook、opening、CTA 或发布包生产**：交给 `$cflow-package`。

不能路由的情况：

- 用户要求查资料、查证事实、找来源、找数据、找真实案例、整理引用或 source pack，`cflow-research` 必须先承担。
- 用户问“这个说法能不能写、有没有来源、事实是否成立”，`cflow-research` 必须自己给判断和安全写法。
- 用户提供来源但不确定能不能用，`cflow-research` 必须先判断来源等级、限制和可用性。
- 下游需要证据缺口补齐，`cflow-research` 必须先补证据并标注不能支持的部分。
